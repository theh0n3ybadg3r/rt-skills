Red Team Skills: Architecture

An AI-assisted, human-led operating model that turns an intake request into verified, objective-based red team deliverables, built as composable Skills for Claude Code and Codex. It follows a threat-informed, intelligence-led red team methodology: a capability-building and control-validation function, not an independent assurance function.

1. What this is

Eight composable skills: a six-phase engagement lifecycle that begins at intake, a cross-cutting independent verifier, and one standalone vulnerability capability. The six phase skills carry an engagement from intake to closure, handing off over one shared artifact. Each skill is markdown instructions the coding agent follows; the bundled code is small stdlib Python helpers, including validate.py (technique- and control-ID validation and the release gate) and export.py (optional, additive machine formats). Document conversion uses two external prerequisites: pandoc (.docx sources in, .docx deliverables out) and pdfplumber (.pdf sources in), wrapped by pandoc_convert.py and pdf_convert.py. The design goal is trustworthy automation: the machine does the tedious work and the checkable validation, and a human stays in command of authorization, execution, and release.

Engagements are objective-based: an objective is a business outcome with a measurable success criterion, not a flag, a technique, or a vulnerability class. Three principles shape everything below: many small composable skills rather than one monolith; verification runs in an independent context; and anything checkable is checked by deterministic code, not by the model that might have gotten it wrong.

2. The pipeline

Six phase skills hand off over one shared artifact. Two authorization gates govern the run, an independent reviewer gates each producing phase fail-closed, and a human authorizes execution and release.

  1. rt-govern (Phase 1, Intake and Scoping) turns an intake request into an outcome-based Scoping Document: it elicits the business impact from the stakeholder and validates it against the enterprise business-impact analysis, derives the crown-jewel targets, drafts measurable objectives, sets the data class and egress policy, and captures the Gate 1 sign-off. Nothing downstream runs without a signed Scoping Document.
  2. rt-intel (Phase 2, Threat Intelligence and Objective Design) selects an intelligence-justified threat actor per objective and maps each actor's techniques to ATT&CK/ATLAS/AADAPT with verbatim citations, confirms the engagement type, and writes the Threat Profile Brief. It enriches the approach without changing the signed intent.
  3. rt-emulate (Phase 3, Attack Planning) turns the Scoping Document and Threat Profile into the Engagement Planning Pack Part A: a hypothesized attack path per objective, each step a validated technique that is actor-consistent, with a detection risk and a branch if blocked. It records the Gate 2 (Rules of Engagement) sign-off, which authorizes execution.
  4. rt-adapt (Phase 4, Execution and Live Testing) supports execution under a signed RoE: it structures and appends the contemporaneous engagement log and proposes validated variant options when a technique is blocked or detected (decision support). The human operator decides and executes; rt-adapt executes nothing and never fabricates the log.
  5. rt-report (Phase 5, Reporting) reconciles the Execution Record against the Blue Team Account to measure unaided detection, establishes findings that name systems, controls, and processes but never an individual, and renders the Engagement Report and the Executive Summary. Material findings escalate to the CISO.
  6. rt-handoff (Phase 6, Handoff and Closure) routes each finding into the enterprise system that will own it (vulnerability management or control tracking), equips the retest function, confirms cleanup and infrastructure decommission, and closes the engagement tracker.
  7. rt-verify (cross-cutting) runs in an independent context and gates each producing section fail-closed across four targets (scoping, threat-profile, planning, report). Under Claude Code that context is the rt-engagement-verifier sub-agent it dispatches; on Codex it is a fresh session.

3. The shared artifact

One markdown file, engagements/<id>/engagement.md, carries the whole run. Each skill writes only its own section, in numbered order, and never modifies another skill's block. Every section carries a machine-readable JSON block the validate helper can parse.

1. Scoping Document (rt-govern)
objectives as outcomes, crown jewels, data class, egress, Gate 1 sign-off.
2. Threat Profile (rt-intel)
intelligence-justified actor per objective, techniques with verbatim citations.
3. Planning Pack (rt-emulate)
attack path per objective, detection risk, branches, Gate 2 (RoE) sign-off.
4. Execution Record (rt-adapt)
contemporaneous log, detection observations, cleanup, recovered-secret types.
5. Report (rt-report)
Blue Team Account, Detection Analysis, findings with control-domain mapping.
6. Handoff and Closure (rt-handoff)
findings routed to enterprise systems, retest handoff, tracker closure.
7. Verification (rt-verify)
per-item verdicts and the release ready flag, one block per target.
Provenance
each section records the catalog versions used, for the audit trail.

4. Human-ready and machine formats

The Phase 5 deliverables are human documents: the Engagement Report and the Executive Summary, each in markdown, a self-contained HTML rendering, and an editable docx via pandoc. The methodology mandates no machine-format deliverable.

Human-ready
markdown, a self-contained HTML rendering (inline CSS, no external assets, ASCII-clean, light/dark aware; print it to PDF from any browser), and an editable docx rendered with pandoc. The intake and engagement artifact render to docx too.
Machine formats (export.py, optional and additive)
where a downstream SIEM, threat-intel platform, or ML pipeline asks for one: structured JSON, a STIX 2.1 bundle, and ATT&CK Navigator layers. Not required, and skipped unless a consumer asks.

export.py re-serializes content the phase skills already produced and rt-verify already validated; it re-serializes, it does not re-validate. STIX is framework-neutral and carries all three offensive frameworks; the Navigator layers are ATT&CK-enterprise only, so ATLAS and AADAPT techniques ride in the STIX bundle rather than being forced into the layer. (export.py is being updated for the v3 schema and the real deliverable names in a later tooling pass; the Engagement Report and Executive Summary are the Phase 5 deliverables regardless.)

Standalone: vulnerability exposure (rt-exposure)

Not every request is a full engagement. rt-exposure (alias rt-vuln) is a standalone skill for on-demand subject-matter expertise on a newly disclosed vulnerability. It does not require an rt-govern authorization and does not write the engagement artifact; it reads the supplied advisory or CVE and writes its own exposure-assessment/v1 artifact under exposures/<vuln-id>/exposure.md. It reuses the same machinery: the validate helper, the local document converters, and the independent-verifier pattern.

It dissects the vulnerability (weakness / CWE, affected surface, exploitation path mapped to ATT&CK/ATLAS/AADAPT, and severity signals, each grounded in a verbatim quote), judges whether the organization is exposed, and proposes compensating controls. Each control is mapped to a NIST CSF Category and/or a NIST SP 800-53 control (verbatim citations), with an explicit limits-exposure claim and a stated residual risk. Two independent verifiers gate it fail-closed, one for the dissection and one for the controls, dispatched as the rt-exposure-verifier sub-agent (target dissection, then controls). Where the data class is public-reference (public CVEs), the verifiers can run on a different model than the producer for uncorrelated errors, within the data-class boundary.

5. Deterministic vs model-driven

This split is why verification can be trusted. Checkable facts are checked by code; only the genuinely semantic judgment is left to the model.

Technique or control ID exists, ID type, official-name match, the release gatedeterministicGround-truthable against the catalog. A model must not self-report these.
Which techniques the intelligence describes, and the quote for eachmodelReading comprehension over prose.
Whether an objective is an outcome, a quote supports a mapping, a step is actor-consistent, a finding traces to the recordmodelThe irreducibly semantic calls (the four rt-verify targets).

The same split applies to rt-exposure: the validate helper checks NIST CSF and NIST SP 800-53 control IDs and names against their vendored catalogs, while the two verifiers judge whether the dissection is faithful and whether each control genuinely limits the exposure.

6. The fail-closed gate

Release is computed by validate.py's gate mode, not typed by the model. An item is confirmed only when its ID (and name, if given) validate, a cited quote resolves, and the persona judgment for that target is yes. The artifact is ready only when there is at least one verdict and every verdict is confirmed (so a dropped failing item cannot pass).

fail closed An empty verdict set is never ready. If the catalog is unreachable, items become unverifiable and the artifact is gated. Nothing is ever silently passed.

7. Data-class model and its honest limit

Every run declares a data class. public-reference input may egress; engagement-sensitive input must not. The load-bearing idea: the public framework catalog is not source content, so fetching it to validate IDs is always allowed, even on a sensitive run. The helper honors this fully; it sends only catalog requests, never source text.

limitation The reasoning is done by the model. With a hosted model, that inference sends the source content to the model provider, which is itself egress. So source_content: false is a hard guarantee only with a local model or an enforced boundary. The design states this rather than overclaiming.

8. Catalog sourcing and maintenance

ATT&CK and ATLAS self-update; the rest are vendored. This is the whole maintenance surface (see MAINTENANCE.md).

  • ATT&CK and ATLAS: fetched live from MITRE (always-latest STIX / latest release), cached 24h. New techniques appear automatically.
  • AADAPT: no live JSON endpoint, so a small version-pinned catalog is vendored and re-synced with sync_aadapt.py (which prints a review diff). validate.py --catalog-info reports versions and warns when it is stale.
  • NIST 800-53 and NIST CSF (the control frameworks used by rt-report and rt-exposure): also vendored, re-synced with sync_nist80053.py and sync_csf.py. Both NIST OSCAL and CSF sources are U.S. government work in the public domain.

9. Cross-platform by construction

All domain knowledge lives in portable references/*.md. The SKILL.md (Claude Code) and AGENTS.md (Codex) files are thin adapters over the same references, so the two platforms share one core and Devin is a later port rather than a rewrite. Where a platform lacks per-agent model selection, everything runs on the inherited model.

10. Where this sits

Eight skills: a six-phase engagement pipeline (rt-govern, rt-intel, rt-emulate, rt-adapt, rt-report, rt-handoff), the cross-cutting independent verifier (rt-verify), and the standalone vulnerability-SME capability (rt-exposure) alongside them. Planned follow-ons include coverage and detection-gap skills for purple-team closure, seeding rt-emulate directly from the MITRE CTID library by adversary name, and packaging so the /rt-* commands install as slash commands.
