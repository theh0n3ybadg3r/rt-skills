Cross-Provider Verification

How to run the independent verification pass on a different model provider from the one that produced the engagement artifact, for example Codex on a GPT model verifying what Claude Code produced, and the data-class rule that decides when you are allowed to.

Why a different provider

Verification in this system has two halves, and only one of them gains from a second vendor.

deterministic

The machine check

validate.py checks every technique and control-domain ID by code: its shape, its existence in the authoritative catalog, and its official name. This is stdlib Python that runs locally. It is already independent of any model and does not change when you switch the verifier's provider.

semantic

The judgment

Whether a quote actually supports a mapping, whether an objective is an outcome, whether a finding traces to the log: these are judgments a model makes. Running them on a genuinely different vendor's model produces uncorrelated errors. A Claude blind spot is not shared by GPT.

This is the strongest form of the independence the design already aspires to. The #verification block records it: every block carries producer_model, verifier_model, and boundary, so the audit trail shows which model produced the work and which model checked it.

The rule that governs it: the data class

read this first

The verifier receives the source content, it re-reads the cited sources to confirm each quote is present verbatim. So the choice of verifier host is an egress decision, and the engagement's data class governs it. Sending source content to a different vendor or host is egress across a boundary.

Data classCross-vendor verificationWhy
public-reference Allowed, and preferred for independence. The source is already public (published CVEs, advisories). Sending it to another vendor is not a new disclosure. This is the common case for rt-exposure.
engagement-sensitive Only on an authorized host. Otherwise a blocker, not a fallback. Target-derived intelligence must stay on the authorized boundary. A public consumer Codex or GPT account is not that boundary and using it violates the data-class policy. Use an enterprise OpenAI or Azure OpenAI deployment under the same no-train, no-retain terms the organization sanctioned, or keep the verifier on the authorized boundary (a different Claude tier still gives a fresh context).

This matches the rule in skills/_shared/references/degradation.md (KTD4) and rt-verify. Cross-vendor verification does not relax it: independence never justifies egressing engagement-sensitive content across an unauthorized boundary.

The operational workflow (available today, no new code)

The skills ship a Codex adapter (AGENTS.md) for every skill, and Codex runs a GPT model. So you can produce the engagement in Claude Code and run the verify pass in Codex, using the two harnesses as two independent contexts on two vendors. Nothing new is required.

  1. Produce in Claude Code. Run phases 1 to 6 (/rt-govern through /rt-report and /rt-handoff). The artifact is engagements/<id>/engagement.md; the cited sources sit beside it.
  2. Open a fresh Codex session for the verify pass. Give it only the engagement artifact, the cited sources, and validate.py. Do not hand it the Claude producer's reasoning: the point of a fresh context is that it never saw how the work was produced.
  3. Run the reviewer per target. For the engagement artifact, verify each of scoping, threat-profile, planning, and report; for a standalone exposure assessment, run the two verifiers (dissection and controls). The reviewer re-derives each verdict from the artifact, the sources, and live catalog data (validate.py --entries ... --refresh), and returns the #verification block. It does not reuse the producer's script_verdict.
  4. Write the block and compute the gate. Run validate.py --gate <block> --expect-ids <ids>. It returns ready only when every verdict is confirmed and every expected ID is covered. Record producer_model (the Claude model), verifier_model (the GPT model), and boundary (cross-vendor-permitted-public-reference, or the authorized-host value for a sanctioned enterprise endpoint).

In the existing design, running the verifier in Codex is listed as a fallback for when a named agent is unavailable. Used deliberately across vendors, it is a first-class independence choice, not a degradation.

What does not change

Whichever model renders the judgment, the trust floor is the same code. validate.py and the fail-closed gate run locally and are vendor-agnostic: a catalog it cannot reach is still unverifiable, an empty verdict set still never passes, and --expect-ids still prevents dropping a failing item to sneak past. Switching providers strengthens the semantic-independence claim; it does not touch the deterministic checks.

Future work: automated cross-provider dispatch

not implemented

A future option is to make the cross-provider verify pass a single command rather than a manual harness switch: a bundled helper that shells out to a provider CLI (codex exec) or an OpenAI-compatible API for the semantic pass and returns the #verification block. It would enforce the data-class gate in code, refusing to send engagement-sensitive source to an unauthorized boundary.

The tradeoffs are why it is not built today: it adds a third-party dependency, credential handling, and an egress surface, and it moves away from the current stdlib-only, one-bundled-validation-helper design. It is recorded here as a roadmap option, not a shipped feature.
